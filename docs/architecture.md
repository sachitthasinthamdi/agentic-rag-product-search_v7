> **ข้อสรุปที่ควรเขียนในเล่ม ไม่ใช่ "LLM คุม agent แล้วดีขึ้น" แต่เป็น**
> **"ไม่ใช่ทุกการตัดสินใจควรยกให้ LLM — และเราวัดได้ว่าข้อไหนควร ข้อไหนไม่ควร"**
> ซึ่งตรงกับข้อค้นพบหลัก: LLM เก่งตัดสินเรื่องภาษา ไม่เก่งตัดสินเรื่องตัวเลข

> **บทเรียนที่ควรบันทึก:** ร่างแรกของเอกสารนี้เรียกสถาปัตยกรรมว่า multi-agent
> โดยแค่เปลี่ยนชื่อโมดูลเดิม (Memory→Host, Planner→Supervisor, Retriever→Search Agent,
> Reranker→Curator Agent) ซึ่งเป็นการตั้งชื่อ ไม่ใช่การออกแบบ
> เป็นกับดักที่พบบ่อยในงานด้านนี้ — **ถ้าแผนภาพกล่องเหมือนกัน ก็ไม่ใช่สถาปัตยกรรมใหม่**

## A1 — RAG ธรรมดา

```
คำถาม ──▶ Retriever ──▶ Generator ──▶ ตอบ
```

ไม่มีความจำ · ไม่มีการวางแผน · ไม่มีการจัดอันดับ · ค้นด้วยข้อความที่ผู้ใช้พิมพ์ตรง ๆ
**เรียก LLM 2 ครั้ง** สำหรับคำถามไทย (ชั้นแปล + Generator) · **1 ครั้ง** สำหรับคำถามอังกฤษ

**คืนสินค้า 3 ชิ้น เท่ากับแขนอื่น** (`TOP_K = 3`) — ตั้งให้เท่ากันตอนขั้นที่ 8 เพราะเดิม
คืน 5 ชิ้นแล้วทำให้ตัวชี้วัดคิดจากคนละฐาน เทียบกันไม่ได้
**สิ่งที่ยังต่างคือ A1 ไม่มีชั้นคัดเลือก** — 3 ชิ้นของ A1 คือ 3 อันดับแรกของ cosine ตรง ๆ
ส่วน A2-A4 คัดมาจากผู้เข้าชิง 100 ชิ้น

⚠ **A1 ใช้โหมดอ่อนของ Generator ไม่ได้** เพราะไม่มี Reranker จึงไม่รู้ว่าผลค้นอ่อน
→ เป็นข้อจำกัดเชิงโครงสร้างของเส้นฐาน **ไม่ใช่สิ่งที่ควรกลบ**

## A2 — Pipeline agent (ของเดิม)

```
Memory ──▶ Planner ──▶ Retriever ──▶ Reranker ──▶ Generator
              │
              ├──▶ ถามกลับ
              └──▶ คุยทั่วไป
```

**Planner ทำงานรอบเดียว** เลือก 1 จาก 3: `ask` / `recommend` / `chat`
ส่งต่อไปข้างหน้าทางเดียว **ไม่มีใครย้อนกลับได้**
**เรียก LLM 4 ครั้ง** สำหรับคำถามไทย (Memory · Planner · **ชั้นแปล** · Generator)

> ⚠ **Reranker ของ mark6 ไม่เรียก LLM** — ต่างจาก A2 ต้นฉบับใน `agentic-rag-demo`
> ที่ให้ LLM ให้คะแนน 0-10 · เปลี่ยนเป็นตัวเลขล้วนเพราะ mark5 วัด LLM-as-judge
> ได้ κ = 0.08-0.25 (ดู `reranker_plan.md` ข้อ 6)

### ⚠ ทำไมไม่ใช่ Planner ตัวเดียวที่เลือก 4 ตัวเลือกตามแผนเดิม

แผนเดิมกำหนดว่า Planner ถูกเรียกทุกรอบและเลือก `ask` / `chat` / `search` / `answer`
**ขั้น 5.6 ทดสอบแล้วพบว่าโมเดลทำแบบนั้นไม่ได้**

| วิธีถาม | ความแม่น | Cohen κ | ผลที่ได้ |
|---|---|---|---|
| ให้เลือกชื่อการกระทำ (แผนเดิม) | 41.7% | **0.000** | **ตอบ `search` ทั้ง 12 ข้อ** |
| สลับลำดับตัวเลือก | 41.7% | 0.000 | เหมือนเดิม — ไม่ใช่เรื่องลำดับ |
| **ถามเป็นคำถามใช่/ไม่ใช่** | **83.3%** | **0.676** | ← **ที่ใช้จริง** |

**ถ้าสร้างตามแผนเดิม A4 จะวนจนครบเพดานทุกครั้งโดยไม่เคยตัดสินใจเลย**

จึง**แยกเป็น 2 ฟังก์ชัน** ให้แต่ละอันถามในรูปที่โมเดลตอบได้

| ฟังก์ชัน | เรียกเมื่อไหร่ | ตัวเลือก | ใครตัดสิน |
|---|---|---|---|
| `planner.decide()` | 1 ครั้งต่อรอบสนทนา | `ask` · `chat` · `recommend` | LLM (κ=0.646 · ดีกว่าโค้ด 0.280) |
| `planner.decide_loop()` | **ทุกรอบของลูป** | ค้นใหม่ / พอแล้ว | **A3 = โค้ด · A4 = LLM** |

> **ยังตรงเจตนาเดิมของสถาปัตยกรรม** — มีการตัดสินใจทุกรอบของลูปจริง
> และ A3 กับ A4 ยังต่างกันแค่ตัวแปรเดียว · เปลี่ยนแค่**รูปของคำถาม** ให้ตรงกับที่โมเดลทำได้

### A3 กับ A4 ต่างกันที่ฟังก์ชันเดียว

> ⚠ **วัดแล้วก่อนสร้าง (ขั้น 5.6 · `tools/test_planner.py`)**
>
> | วิธีตัดสินว่าจะวนซ้ำไหม | ความแม่น | Cohen κ |
> |---|---|---|
> | LLM แบบ "เลือก action" (ที่ออกแบบไว้แรก) | 41.7% | **0.000** — ตอบ `search` ทุกข้อ |

> **แต่ A4 ต้องใช้พรอมต์แบบถามใช่/ไม่ใช่** ไม่ใช่แบบเลือก action ไม่งั้นเป็นการจัดฉากให้แพ้

| | **A3 — โค้ดตัดสิน** | **A4 — LLM ตัดสิน** |
|---|---|---|
| ฟังก์ชัน | `a3.should_search_again()` | `planner.decide_loop()` |
| กฎการวน | `ถ้าผ่านประตู < 3 ชิ้น และค้นมาไม่เกิน 3 ครั้ง → ค้นใหม่` | ถาม LLM ว่า "ของพอจะแนะนำ 3 ชิ้นไหม" |
| LLM เพิ่มต่อรอบลูป | **+0** | **+1** |
| ทำซ้ำได้ | ⚠ **ไม่ใช่ 100%** — ตัวเขียนคำค้นใหม่ใช้ LLM (เหมือนกันทั้งสองแขน) | ⚠ ไม่ 100% จากทั้งสองจุด |
| เรียกว่า agentic | ✅ ใช่ — LLM วางแผนการกระทำ + เขียนคำค้นเอง (แต่ไม่ได้คุมการวน) | ✅ ใช่เต็มรูปกว่า |
| **เป็นระบบที่แนะนำให้ใช้** | ✅ **ใช่** | ❌ แพงกว่า 34% โดยไม่ได้ผลดีกว่า |

**ต่างกันแค่ตรงนี้** ส่วนอื่นเหมือนกันทั้งหมด → เป็นการเปลี่ยนตัวแปรทีละตัวอย่างแท้จริง

**เพดานจำนวนรอบเป็นของโค้ดทั้งสองแขน** (`MAX_SEARCHES = 3`) เพราะเป็นเรื่องความปลอดภัย
ไม่ใช่การตัดสินคุณภาพ · A4 จึงเป็น **โค้ดคุมกรอบ · LLM ตัดสินภายในกรอบ**

## แผนที่โมเดล — โมเดลไหนอยู่จุดไหน

**สถานะ: แผน** ตอนนี้ยังสืบทอดจาก A2 คือ **Typhoon ทุกจุดที่เป็น LLM**

```
                    Memory ◀── JSON
                       │
                       ▼
            ┌────────────────────┐
       ┌───▶│      Planner       │───▶ Generator ◀── ร้อยแก้วไทย
       │    │       JSON         │───▶ ถามกลับ   ◀── ร้อยแก้วไทย
       │    └────┬──────────┬────┘───▶ คุยเล่น   ◀── ร้อยแก้วไทย
       │         │          │
       │   ┌─────▼────┐ ┌───▼──────┐
       │   │Retriever │ │ Reranker │◀── JSON
       │   │  bge-m3  │ └───┬──────┘
       │   │ + ชั้นแปล │     │
       │   └─────┬────┘     │
       └─────────┴──────────┘
              รายงานกลับ
```

| จุด | งาน | รูปแบบ | โมเดล |
|---|---|---|---|
| Memory | สกัดโปรไฟล์ + จำคำค้นที่ลองแล้ว | JSON | Typhoon |
| **Planner `decide()`** | เลือก 1 จาก **3** (`ask`/`chat`/`recommend`) | JSON | Typhoon |
| ชั้นแปล | แปลคำค้น ไทย→อังกฤษ · **อังกฤษไม่เรียก** | ข้อความสั้น | Typhoon |
| **ตัวเขียนคำค้นใหม่** | คิดคำค้นใหม่ตอนลูปวน | ข้อความสั้น | Typhoon |
| Retriever — ค้น | หาสินค้าใกล้เคียง | เวกเตอร์ | **bge-m3** |
| **Reranker** | คัด 4 ชั้น + รายงาน `n_passed` | **ตัวเลขล้วน** | ❌ **ไม่มีโมเดล** |
| Generator — แนะนำ | เขียนคำแนะนำ | ร้อยแก้วไทย | Typhoon |
| **Generator — โหมดอ่อน** | ของไม่ถึง 3 ชิ้น → ลิสต์ข้อเท็จจริง | — | ❌ **โค้ดเขียนเอง** |
| ถามกลับ (`ask`) | เขียนคำถาม | ร้อยแก้วไทย | Typhoon |
| คุยเล่น (`chat`) | ตอบทั่วไป | ร้อยแก้วไทย | Typhoon |
| **ตัดสินลูปของ A3** | วนซ้ำไหม | — | ❌ **โค้ด** |
| **ตัดสินลูปของ A4** | วนซ้ำไหม | JSON | **Typhoon** (`decide_loop()`) |

**A3 กับ A4 ใช้โมเดลเหมือนกันทุกจุด ต่างกันแค่ 2 แถวล่างสุด**

> ⚠ ตารางเดิมเขียนว่า **Reranker ใช้ Typhoon** ซึ่งไม่จริง — ของ mark6 เป็นตัวเลขล้วน
> และเดิมเขียนว่า Planner เลือก 1 จาก 4 ซึ่งไม่ตรงกับโค้ด (แยกเป็น 2 ฟังก์ชัน)

### ข้อเสนอที่ยังไม่ตัดสิน — แยกโมเดลตามประเภทงาน

ใน **A4 วน 2 รอบ** เรียก LLM 7 ครั้ง แยกได้เป็น:

| | จำนวน | ต้องเขียนไทยสวยไหม |
|---|---|---|
| Memory 1 + Planner 3 + Reranker 2 + ชั้นแปล 2 | **8 ครั้ง** | ❌ ไม่ต้องเลย |
| Generator | **1 ครั้ง** | ✅ ต้อง |

**8 ใน 9 ครั้งไม่ได้ใช้ความเก่งภาษาไทยของ Typhoon** ใช้แต่ความสามารถตอบตามรูปแบบ
ซึ่งเป็นด้านที่**ยังไม่ได้วัด** → ดูข้อ 2 ใน "การตัดสินใจที่ยังค้าง"

ถ้าแยก: เปลี่ยน 4 กล่อง (Memory · Planner · Reranker · ชั้นแปล) ไปใช้โมเดล JSON
ส่วน 3 กล่องร้อยแก้วไทยคงเป็น Typhoon

**VRAM:** เครื่องนี้มี 8,188 MiB ใช้ไปแล้ว ~1,712 เหลือ ~6.4 GB

| ชุด | รวม | ผล |
|---|---|---|
| ตอนนี้ — Typhoon 4.9 + bge-m3 1.2 | 6.1 GB | ✅ ไม่ต้องสลับ |
| ถ้าแยก — Typhoon 4.9 + JSON ~2.0 + bge-m3 1.2 | 8.1 GB | ⚠ เกิน ต้องสลับ |

แต่รับได้ เพราะ**กล่องร้อยแก้วไทยทั้ง 3 อยู่ท้ายรอบเสมอ** ไม่ว่า Planner เลือกทางไหน
→ งาน JSON ทุกตัวเกิดติดกันหมด แล้วสลับไป Typhoon ครั้งเดียวตอนจบ = **สลับ 1 ครั้งต่อรอบ** (~2-4 วินาที)

> ⚠ **ข้อบังคับเพื่อความถูกต้องของผลเทียบ:** ชุดโมเดลต้อง**เหมือนกันทั้ง A1-A4**
> ไม่งั้นจะแยกไม่ออกว่าผลที่ดีขึ้นมาจากลูป หรือมาจากการเปลี่ยนโมเดล

อธิบายหลักฐาน 6 ชิ้นที่พบระหว่างทาง (เมินตัวอย่างในพรอมต์ · ละเมิดกฎของตัวเอง ·
ย่อพรอมต์ครึ่งหนึ่งไม่เปลี่ยน · ใส่ป้ายไม่เปลี่ยน · ตีความประวัติผิด · ตอบค่าคงที่)
→ และอธิบายว่าทำไมการออกแบบที่เลือกไว้ถูก

---

## การตัดสินใจที่ปิดแล้ว / ที่ยังค้าง

| # | เรื่อง | สถานะ |
|---|---|---|
| 1 | **ทำ `decompose` ไหม** (แตกโจทย์เป็นงานย่อย แล้วค้นขนานกัน) | ❌ **ตัดออก** — เหตุผลเดียวที่ต้องมีคือเพื่อรองรับคำว่า multi-agent · หัวข้อไม่ได้บังคับ → ไม่คุ้มกับงานที่เพิ่มและการขยายขอบเขตโจทย์ · ถ้าเหลือเวลาค่อยทำเป็นส่วนเสริม |
| 2 | **ทดสอบ Planner ของ Typhoon ก่อนไหม** | ✅ **ทำแล้ว (ขั้น 5.6)** — 29 สถานการณ์ × 3 รอบ · ผล: Planner คุ้มที่จะใช้ LLM (κ 0.646 vs 0.280) แต่**การตัดสินลูปควรใช้โค้ด** (κ 0.824 vs 0.676) · **และต้องเปลี่ยนรูปคำถามของ A4 ไม่งั้นได้ κ=0.000** |
| 3 | **ชั้นแปลภาษาไทย→อังกฤษ** | ✅ **ต้องมี** — ผลทดสอบสองภาษาในขั้น 4.4: ทับซ้อน@5 เพียง 25.3% · คะแนนฝั่งไทยต่ำกว่าทุกคำถาม ~0.08 · ใส่ในขั้นที่ 5 · **ดัชนีไม่ต้องสร้างใหม่** |
