## สถาปัตยกรรม 4 ชั้น — ออกแบบให้ใช้ซ้ำได้กับทุกสถาปัตยกรรมของระบบ

```
ชั้น 4  สถาปัตยกรรมระบบ   RAG ธรรมดา │ Agentic เดี่ยว │ หลาย agent   ← เปลี่ยนได้อิสระ
           ↓ เรียกผ่าน
ชั้น 3  Retrieval API      search(query, k, filters) → ผลลัพธ์       ← หน้าตาเดียว ไม่เปลี่ยน
           ↓
ชั้น 2  Vector store       Chroma local                             ← สร้างครั้งเดียว
           ↓ กู้คืนได้จาก
ชั้น 1  ไฟล์เวกเตอร์       bge-m3.npy + ids + meta                  ← ของจริงที่ต้องหวงไว้
```

**เหตุผลที่ต้องแยกชั้น 1 ออกจากชั้น 2:** ถ้าเก็บเวกเตอร์ไว้ในฐานข้อมูลอย่างเดียว
พอฐานพัง/อยากเปลี่ยนฐาน/อยากเทียบสถาปัตยกรรมใหม่ ก็ต้องแปลงใหม่ 37 นาทีทุกครั้ง
แยกเก็บเป็นไฟล์แล้วการสร้างฐานใหม่ใช้เวลาไม่กี่นาที

**สิ่งที่ต่างกันระหว่างสถาปัตยกรรม อยู่เหนือชั้น 3 ทั้งหมด:**

| | RAG ธรรมดา | Agentic เดี่ยว | หลาย agent |
|---|---|---|---|
| ค้นกี่รอบ | 1 | agent ตัดสินเอง | แต่ละ agent ค้นเอง |
| ใครตัดสินว่าค้นอะไร | ผู้ใช้พิมพ์มาตรง ๆ | planner | planner + agent ลูก |
| เครื่องมือ | `search` | `search` + `recommend` | + เปรียบเทียบ/สรุป |

ทั้ง 3 แบบเรียก `search()` ตัวเดียวกัน → **ไม่ต้องสร้างดัชนีใหม่เลย**

# ต้องตัดสิน 4 ข้อ

## ① โมเดลแปลงข้อความเป็นเวกเตอร์

ต้อง**รองรับหลายภาษา** เพราะคำถามมีภาษาไทย แต่ข้อมูลเป็นอังกฤษ

| โมเดล | มิติ | ขนาด | หมายเหตุ |
|---|---|---|---|
| **BGE-M3** (BAAI) ⭐ | 1,024 | 2.2 GB | รองรับ 100+ ภาษา · **มีอยู่บนเครื่องนี้แล้ว** (Ollama) · ใช้กันแพร่หลายในงาน multilingual retrieval |
| multilingual-e5-large | 1,024 | 2.2 GB | ความสามารถใกล้เคียง — เป็นตัวเทียบที่ดีถ้าจะทำเปรียบเทียบในเล่ม |
| paraphrase-multilingual-MiniLM | 384 | 0.5 GB | เล็กเร็วกว่ามาก แต่ความแม่นต่ำกว่าชัดเจน |

**แนะนำ BGE-M3** — มีอยู่แล้ว ไม่ต้องโหลดใหม่ และเป็นตัวที่คนใช้เทียบกันในงานวิจัยด้านนี้

## ② สินค้า 1 ชิ้น = กี่เวกเตอร์

⚠ **เปลี่ยนทีหลังต้องแปลงใหม่ทั้งหมด**

| | 1 ชิ้น = 1 เวกเตอร์ ⭐ | แตกเป็นชิ้นย่อย |
|---|---|---|
| จำนวนเวกเตอร์ | 81,264 | ~400,000 |
| เวลาแปลง | ~37 นาที | ~3 ชั่วโมง |
| ผลการค้น | ได้สินค้าตรง ๆ | ต้องรวมผลหลายชิ้นกลับเป็นสินค้า |
| เหมาะกับ | "แนะนำสินค้า" | "หาข้อมูลในเอกสารยาว" |

**แนะนำ 1 ชิ้น = 1 เวกเตอร์** — ผลลัพธ์ที่ต้องการคือสินค้า ไม่ใช่ย่อหน้า
และ `embed_text` มัธยฐานแค่ 1,909 ตัวอักษร ยังไม่ยาวพอที่การแตกชิ้นจะช่วยมาก

> ถ้าอยากเทียบในเล่มภายหลัง สร้างเป็น collection แยกได้ ไม่กระทบอันเดิม

# สิ่งที่จะเก็บ

## ชั้น 1 — ไฟล์เวกเตอร์ (ของจริงที่ต้องหวง)

```
data/vectors/
  bge-m3_v1.npy          เวกเตอร์ 81,264 × 1,024 (float16) = 166 MB
  bge-m3_v1.ids.feather  parent_asin เรียงตรงกับแถวใน .npy
  bge-m3_v1.meta.json    ชื่อโมเดล · มิติ · วันที่ · sha256 ของ embed_text ทั้งคอลัมน์
```

`.meta.json` มี sha256 ของ `embed_text` → **ตรวจอัตโนมัติได้ว่าเวกเตอร์ตรงกับข้อความปัจจุบัน
หรือล้าสมัยแล้ว** (ถ้าแก้ `embed_text` แล้วลืมแปลงใหม่ จะรู้ทันทีไม่ใช่รู้ตอนผลค้นเพี้ยน)

## ชั้น 2 — Chroma local

collection ชื่อ **`products_bge-m3_v1`** (ชื่อบอกโมเดล + เวอร์ชันของ `embed_text`)
→ ถ้าวันหนึ่งแก้ `embed_text` ก็สร้าง `v2` **อยู่ด้วยกันได้ ไม่ทับกัน** เทียบผลข้ามเวอร์ชันได้

เก็บ 4 อย่างต่อสินค้า:

| | เก็บอะไร | ทำไม |
|---|---|---|
| id | `parent_asin` | เชื่อมกลับไปหาข้อมูลเต็ม |
| vector | 1,024 ตัวเลข | ตัวที่ใช้ค้น |
| document | `embed_text` | ตรวจได้ว่าทำไมชิ้นนี้ถูกค้นเจอ (สำคัญตอน debug) |
| metadata | `title` `category` `price` `price_tier` `average_rating` `rating_number` `popularity` `value_score` `store` `image` | กรองและแสดงผลโดยไม่ต้องเปิดไฟล์ |

**เก็บ metadata เกินไว้ดีกว่าขาด** — การเพิ่มฟิลด์ทีหลังต้องวนอัปเดต 81,264 รายการ
สถาปัตยกรรมหนึ่งอาจเรียงด้วย `popularity` อีกอันใช้ `value_score` อีกอันกรอง `price_tier`

**ไม่เก็บ** `description` `features` `details_json` `categories` — ยาวมากและอยู่ใน document แล้ว

## บน HuggingFace Hub

อัป 3 ไฟล์ (รวม ~350 MB) · **ไม่อัปโฟลเดอร์ Chroma** เพราะใหญ่กว่า (~1-1.5 GB)
และผูกกับเวอร์ชัน Chroma

```
products_feature.feather   182 MB   ข้อมูล 16 คอลัมน์
bge-m3_v1.npy              166 MB   เวกเตอร์
bge-m3_v1.meta.json          เล็ก   ข้อมูลกำกับ
```

เพื่อนโหลด 3 ไฟล์นี้แล้ว**สร้าง Chroma เองใน 2-3 นาที โดยไม่ต้องแปลงเวกเตอร์ใหม่**
